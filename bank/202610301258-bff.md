# Tarefa: Integrar confirmação de go-live no BFF

Atue como um engenheiro de software sênior especializado em Kotlin, Spring Boot, APIs REST e arquitetura Backend for Frontend.

## Contexto

Temos um BFF responsável por atender o frontend e consumir um backend de migração bancária.

O backend possui o endpoint:

`PUT /migrados/{cnpj}/golive/acknowledgement`

Esse endpoint já foi implementado e testado.

Ele registra de maneira idempotente a primeira confirmação de ciência do go-live de um cliente.

O backend é responsável por gerar e persistir o `notifiedAt`. O BFF não deve gerar timestamps nem acessar diretamente o DynamoDB.

## Objetivo

Expor no BFF:

`PUT /migration/go-live/acknowledgement`

Sem request body, considerando que o CNPJ pode ser obtido de maneira segura a partir do contexto do usuário autenticado.

Se o projeto permitir múltiplos CNPJs por usuário ou exigir o identificador explicitamente, analisar a convenção existente e propor o endpoint adequado antes de implementar.

### 2. Implementar o endpoint REST

`PUT /migration/go-live/acknowledgement`

Comportamento:

- Não receber request body.
- Identificar o CNPJ autorizado por meio do contexto de autenticação existente.
- Não confiar em identificadores arbitrários enviados pelo frontend.
- Encaminhar a requisição ao backend.
- Retornar 204 quando o backend confirmar a operação.
- Preservar o comportamento idempotente.
- Não gerar ou modificar `notifiedAt` no BFF.

### 3. Implementar a integração HTTP

Adicionar ou reutilizar um método no cliente HTTP existente para executar:

`PUT /migrados/{cnpj}/golive/acknowledgement`

Requisitos:

- Reutilizar autenticação e configurações do cliente HTTP.
- Preservar os headers de correlação e rastreabilidade conforme as convenções existentes.
- Reutilizar timeout e tratamento de erros existentes.
- Não criar outro cliente HTTP se já existir um apropriado.
- Não adicionar dependências sem necessidade.
- Não implementar retries que possam provocar comportamento inesperado; respeitar a política existente.

### 4. Tratar os retornos

Mapear os resultados do backend conforme os padrões atuais do BFF:

- 204: confirmação registrada ou já existente.
- 400 do backend: tratar como falha de integração, pois o CNPJ vem do contexto autenticado e não do frontend.
- 401/403 gerados pelo BFF: aplicar o padrão existente de autenticação e autorização.
- 401/403 do backend: tratar como falha de integração, sem repassar ao frontend como sessão inválida.
- 404: cliente não encontrado.
- 5xx ou erro de comunicação: aplicar o tratamento existente para falhas em serviços dependentes.

Não retornar 204 quando o backend falhar.

Evitar expor mensagens técnicas ou informações internas ao frontend.

### 7. Criar testes automatizados

6. Backend indisponível ou retornando erro.
