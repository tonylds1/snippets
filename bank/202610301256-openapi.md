# Implementação do contrato OpenAPI — Confirmação de go-live

Atue como um engenheiro de software sênior especializado em OpenAPI, REST, contratos de APIs e arquitetura de microsserviços.

## Contexto

Existe um backend de migração bancária com recursos identificados por CNPJ.

Estamos implementando a funcionalidade de confirmação de ciência da comunicação de go-live.

O backend possui um item no DynamoDB que representa o cliente migrado e terá os atributos:

- `dataGoLive`: data prevista para o go-live.
- `notificadoEm`: instante da primeira confirmação de ciência.

Ordem de entrega: contrato OpenAPI, depois backend, depois BFF.

`dataGoLive` é gravado por um processo externo fora deste escopo. A confirmação é independente desse atributo.

Este repositório contém exclusivamente o contrato OpenAPI da API.

## Objetivo

Adicionar ao contrato o endpoint:

`PATCH /migrados/{cnpj}`

Nesta entrega, essa operação apenas registra de maneira idempotente que o cliente tomou ciência da comunicação de go-live.

## 2. Criar a operação PATCH

Endpoint:

`PATCH /migrados/{cnpj}`

Request body:

```json
{ "notificado": true }
```

Definição funcional:

Registra a primeira confirmação de ciência do go-live do cliente identificado pelo CNPJ.

Requisitos:

- O CNPJ é recebido por path.
- O request body é obrigatório e usa `application/merge-patch+json`. Se o padrão do contrato for outro, apontar a divergência no plano.
- O schema aceita somente o campo `notificado`, obrigatório e com o valor `true`.
- Definir `additionalProperties: false`.
- `notificadoEm` não faz parte do payload.
- O timestamp é gerado pelo backend.
- Requisições repetidas preservam a primeira confirmação.
- Nenhum outro atributo do cliente deve ser alterado.
- A operação não depende de `dataGoLive`: cliente existente sem esse atributo também recebe 204.

Reutilizar o parâmetro CNPJ já existente no contrato, caso disponível.

## 3. Definir as respostas

Documentar de acordo com os padrões existentes:

- 204 No Content: confirmação registrada ou já existente.
- 400 Bad Request: parâmetro ou payload inválido, incluindo body vazio, `notificado` diferente de `true` e campos desconhecidos.
- 401 Unauthorized: ausência ou invalidade da autenticação.
- 403 Forbidden: acesso não autorizado ao recurso.
- 404 Not Found: cliente migrado inexistente.
- 5xx: falhas do servidor conforme as convenções existentes.

Não definir response body para HTTP 204.

Utilizar componentes de resposta já existentes sempre que possível.
