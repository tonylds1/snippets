# Tarefa: Implementar confirmação de ciência do go-live

Atue como um engenheiro de software sênior especializado em Kotlin, Spring Boot, APIs REST e AWS DynamoDB.

## Contexto

Temos um backend responsável por armazenar informações de clientes em processo de migração bancária.

Cada item do DynamoDB representa um cliente migrado. O CNPJ é único: cada CNPJ possui no máximo um item.

Precisamos adicionar dois atributos diretamente ao item existente, sem criar uma nova tabela ou um Map genérico:

- `goLiveDate`: data prevista para o go-live, gravada por um processo externo fora deste escopo.
- `notifiedAt`: timestamp da primeira vez em que o cliente tomou ciência da comunicação.

O atributo `notifiedAt` deve permanecer ausente até a primeira confirmação. Não gravá-lo com o tipo `NULL` do DynamoDB.

A confirmação é independente de `goLiveDate`, e essa data não muda depois da ciência.

Ordem de entrega: contrato OpenAPI, depois backend, depois BFF.

## Objetivo

Implementar o endpoint:

`PUT /migrados/{cnpj}/golive/acknowledgement`

A operação deve registrar a primeira confirmação de ciência do go-live e preservar permanentemente o timestamp original em chamadas repetidas.

### 3. Implementar o endpoint

`PUT /migrados/{cnpj}/golive/acknowledgement`

Requisitos:

- Não receber body.
- Obter o CNPJ pelo path.
- Validar o CNPJ conforme os padrões existentes.
- Aplicar os mecanismos de autenticação e autorização já existentes, sem permitir acesso indevido a outro cliente.
- Se a chamada for serviço a serviço, informar no plano qual camada garante que o CNPJ pertence ao usuário.
- Registrar `notifiedAt` com a data e hora atuais do backend.
- Não sobrescrever o timestamp caso ele já exista.
- Não modificar `goLiveDate` nem outros atributos.
- Não exigir `goLiveDate` para registrar a confirmação.
- Retornar HTTP 204 quando a confirmação for registrada ou já existir.
- Retornar HTTP 404 quando o migrado não existir.
- Preservar os padrões existentes de tratamento de erros.

### 4. Garantir idempotência e concorrência

Utilizar uma operação atômica no DynamoDB, preferencialmente `UpdateItem`.

Usar:

`SET notifiedAt = if_not_exists(notifiedAt, :now)`

`:now` é a data e hora atuais geradas pelo backend.

Adicionar uma `ConditionExpression` garantindo a existência do item pelas condições apropriadas à chave primária real da tabela.

Tratar `ConditionalCheckFailedException` como migrado inexistente, retornando 404.

Usar `ReturnValues = UPDATED_OLD` para distinguir a primeira confirmação de uma repetição, caso esse resultado seja usado na observabilidade. Não alterar o status 204 por causa disso.

`if_not_exists` considera existente um atributo com tipo `NULL`: nesse caso, retornaria 204 sem registrar a data. Se não for possível garantir que `notifiedAt` nunca seja gravado como `NULL`, apresentar o problema antes de implementar.

Evitar o padrão de consultar, verificar se está null e depois salvar, pois isso pode introduzir condições de corrida.

Se a abstração atual de persistência não oferecer suporte direto à operação, implementar a solução mais simples compatível com o padrão existente.
